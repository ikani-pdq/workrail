# Reviewer Family: test_docs_rollout

## Findings

1. **No new automated tests** were added for the CI YAML change or the `.mcp.json` launcher -- expected and reasonable: GitHub Actions YAML and MCP client config aren't natively unit-testable in this repo's test suite, and the author substituted **direct empirical execution** as their verification method instead (documented in `docs/design/pilot-security-remediation-final-verification-prover.md`: `execFileSync` runs of both launcher branches, a live `gh pr checks 27` equivalent run, `npm audit`/`typecheck`/`vitest` runs with exit codes captured). I independently re-ran the equivalent checks myself in this review and got matching results -- this substitutes adequately for unit tests given the artifact type.
2. **Documentation is thorough and accurate for the 9 client-config examples** (README.md x2, docs/configuration.md x7) -- each now shows the pinned launcher and explains the `PINNED` variable needs manual updating after a rebuild.
3. **Rollout/migration:** this is a local dev-tooling change (`.mcp.json`, docs) plus a CI job change -- no data migration, no schema change, no `needsSimulation` concern. The CI change's rollout risk is that the newly-strict audit gate could now block merges that previously passed silently; the PR itself demonstrates this was already handled (dependency fixes landed in the same PR, confirmed clean by live CI).
4. **Downstream consumers:** every developer with `.mcp.json`-based Claude Code/Desktop/Cursor config pointed at this repo is a "consumer" of the new launcher. **Finding:** the `PINNED=3.101.1` value is duplicated verbatim across 10 locations (9 docs + live config) with no CI check enforcing they stay in sync, and this repo's own release policy (`AGENTS.md`: semantic-release auto-bumps patch/minor on every merge) means the very next merge to `main` will make the *published package version* drift from all 10 hardcoded copies -- until a human notices and manually updates every occurrence, the MCP server for every dev who rebuilds will refuse to start (fails closed, per `correctness_invariants` -- so it's a friction/DX regression, not a silent-wrong-version risk, but still a real, structurally unaddressed rollout hazard given how this repo's release automation actually behaves).
5. This exact "PINNED" *within-string* duplication was raised by the author's own `final-verification-smells.md` (Orange #1) but their finding was narrower (literal appeared twice inside the one `.mcp.json` string) and **was already fixed** (confirmed: `$PINNED` variable now defined once, referenced twice within that string). The **cross-file** duplication (10 separate copy-pasted occurrences across README/docs/config) is a distinct, broader instance of the same root problem that their own review did not catch and remains open in this diff.

## Verdict
Documentation quality is high and consistent; verification-by-execution is an adequate substitute for unit tests on this artifact type. One real, unaddressed rollout-maintainability gap: **the 10x cross-file PINNED duplication**, which will start causing real friction on this repo's very next automated release. Recommend either consolidating to a single source (e.g., a script reading `package.json`'s own version) or, at minimum, flagging it for a fast-follow before the next release ships.
